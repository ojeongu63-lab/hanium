# 구현 정리 — CNC 이상탐지 MLOps

팀원·멘토가 이 파트를 처음부터 읽고 이해할 수 있도록 최종 구현물을 정리한 문서다.
개발 과정의 시행착오(기각된 접근, 버그 수정 기록)는 여기 담지 않는다 — 각 설계 문서의
"알려진 한계"·"실행 결과에 따른 정정" 절과 `tasks/lessons.md`에 있다. 코드 위치 지도는
[STRUCTURE.md](STRUCTURE.md), 실행 명령은 [README](../README.md) 참고.

## A. 개요

CNC 가공 설비의 공정 센서 데이터로 불량을 사전에 잡는 시스템이다. 실제 제조 현장은
불량 라벨이 거의 없다는 전제를 그대로 따라서, 불량 샘플을 모아 분류기를 만드는 대신
**정상 데이터만으로 학습한 LSTM-Autoencoder의 재구성 오차**로 "평소와 다른 패턴"을 잡는다.

세 단계로 나뉜다.

```
[학습]  원본 CSV → 전처리 → LSTM-AE 학습 → 임계값 → MLflow 등록 → champion 지정
[서빙]  CSV 업로드 → 양품/불량 판정 + 어떤 센서가 벗어났는지 + 현장 조치 가이드
[운영]  드리프트 감지 → 재학습 → 게이트 → 섀도우 → 승격 / 거부(원인 추정 + 조치 제안)
```

## B. 데이터

[KAMP CNC 밀링 공정 데이터셋](https://www.kamp-ai.kr) — 실험(작업) 단위 CSV 25개, 각 실험은
X·Y·Z축과 스핀들(S)의 위치·속도·가속도·전류·전압·파워, 피드레이트까지 48개 컬럼을 기록한다.

- **중복 3개 제외**: 실험14/24는 센서 데이터가 완전히 동일(리키지), 실험19/25는 센서는
  동일한데 라벨이 서로 모순돼 둘 다 신뢰 불가 → 22개 사용.
- **분할**: 학습 8개(정상만) / 평가 14개(정상 3 + 불량 11). 평가셋은 학습에 전혀 관여하지
  않는다 — 임계값도 학습 8개의 오차 분포에서만 정한다(§D).
- **컬럼 41개만 사용**: 48개 중 Z축 전류·전압 관련 4개는 이 데이터셋에서 죽은 채널(상수)이라
  제외, 프로그램 번호·시퀀스 번호·공정 단계명 3개는 시계열 신호가 아닌 메타데이터라 제외.
  근거: [`src/preprocessing/columns.py`](../src/preprocessing/columns.py).

## C. 이상탐지 모델

### C-1. 모델링 — 무엇을 시계열로 보는가, 얼마나 쌓았는가

**시계열 단위는 실험 전체가 아니라 20행짜리 창(window)이다.** 원본 CSV의 한 행은 CNC
컨트롤러의 한 샘플링 tick이고, 41개 채널(축별 위치·속도·가속도·전류·전압·파워 + 피드레이트)이
그 tick의 다변량 벡터다. 모델은 이 벡터가 20개 연속으로 이어진 조각 하나를 통째로 보고
재구성한다 — "다음 값 예측"이 아니라 "이 20-tick 구간이 정상 패턴에서 나올 법한 모양인가"를
묻는 방식이다. 실험(=한 번의 가공 사이클) 하나의 최종 판정은 그 실험 안의 모든 창의
재구성 오차를 모아 하나의 점수로 집계해서 낸다(§D).

- **학습용 창**: 실험별로 겹치지 않게 20개씩 잘라 낸다(tumbling window). 나머지 행은 버린다.
  창 하나를 독립 샘플로 취급해 배치 단위로 섞어 학습한다 — 실험 순서나 창 간의 연속성은
  학습 자체에는 안 쓴다.
- **추론(평가·서빙)용 창**: 1행씩 밀며 만드는 슬라이딩 윈도우(겹침 허용)라, 실험 길이가
  N행이면 창이 N-19개 나온다. 판정 신뢰도를 위해 촘촘하게 여러 번 본다.
- **스케일링**: `StandardScaler`(z-score)를 **학습 8개에만** fit해서 쓴다. 평가·운영
  데이터는 그 스케일러로 transform만 한다 — 평가 라벨을 스케일링에 관여시키지 않는다.

**구조는 인코더 LSTM 1층 + 디코더 LSTM 1층**이다. 스택을 쌓지 않았다 — 학습 데이터가
정상 실험 8개뿐이라 층을 늘려도 이득보다 과적합 위험이 크다고 판단했다.

```
입력 (batch, 20, 41)
  └─ encoder_lstm : LSTM(input=41, hidden=64), 1층
       └─ 마지막 시점의 은닉상태 h_n[-1]  (batch, 64)
            └─ to_latent : Linear(64 → 16)          ← 병목(bottleneck)
                 └─ 잠재벡터를 20번 반복(RepeatVector 방식)
                      └─ decoder_lstm : LSTM(input=16, hidden=64), 1층
                           └─ output_layer : Linear(64 → 41)
출력 (batch, 20, 41)  — 입력과 같은 모양으로 복원 시도
```

인코더가 20-tick 구간 전체를 16차원 벡터 하나로 압축했다가(정보 손실 발생) 디코더가
그 벡터만으로 20-tick을 되살리는 구조다. 정상 패턴은 8개 실험 전체에서 반복되므로 이
병목을 통과해도 잘 복원되지만, 학습 때 없던 패턴(불량)은 16차원에 담기지 않아 복원
오차가 커진다 — 이 오차가 곧 이상 점수다.

- **학습**: Adam(lr=1e-3), batch=64, 손실은 재구성 전체(20×41개 값)에 대한 MSE, 50 epoch.
- 코드: [`src/lstm_ae/model.py`](../src/lstm_ae/model.py),
  [`src/lstm_ae/sequencing.py`](../src/lstm_ae/sequencing.py),
  [`src/lstm_ae/training.py`](../src/lstm_ae/training.py).

### C-2. 임계값과 판정

집계가 두 단계라 "p95"라는 말이 서로 다른 곳에서 두 번 나온다 — 헷갈리기 쉬워 표로 갈음한다.

**1단계 — 실험 하나의 창 여러 개 → 점수 하나.** 실험 하나는 창(20행)이 여러 개고, 창마다
재구성 오차가 하나씩 나온다. 이 여러 오차를 한 실험의 점수 하나로 요약하는 방법이
3가지다: `mean`(평균) · `max`(제일 나쁜 창) · **`p95`①**(상위 5% 지점 — 극단값 한둘은
무시하고 "어지간히 나쁜 정도"를 봄). 학습 실험 8개에 실제 champion 모델을 그대로 돌리면:

| 실험 | mean_score | max_score | p95_score |
|---|---|---|---|
| 1 | 0.595 | 5.170 | 2.250 |
| 2 | 0.970 | 4.820 | 3.108 |
| 3 | 0.609 | 3.912 | 1.571 |
| 11 | 0.373 | 2.903 | 1.397 |
| 13 | 0.400 | 4.278 | 1.807 |
| 14 | 0.394 | 4.515 | 1.361 |
| 15 | 0.646 | 3.943 | 1.628 |
| 17 | 0.362 | 3.219 | 1.500 |

**2단계 — 실험 8개의 점수 8개 → 임계값 하나.** 위 표의 한 열(예: mean_score 8개)을 놓고
그 8개 중 상위 5% 지점(**`p95`②** — 이번엔 실험들 사이에서)을 계산한 값이 임계값이다.
평가 라벨과는 무관하게, 순전히 정상 데이터 8개의 분포에서만 정한다.

| | mean_score 8개의 p95② | max_score 8개의 p95② | p95_score 8개의 p95② |
|---|---|---|---|
| = 임계값 | **0.857** | 5.047 | 2.808 |

세 값 모두 실제 `/predict` 응답의 `threshold`와 일치한다(`method`로 고르는 세 값 그대로).
기본값은 `mean` — 새 CSV의 창 오차를 평균 내 0.857과 비교해 넘으면 불량으로 판정한다.

### C-3. 성능과 한계

평가 실험 14개 기준 **precision 0.91 / recall 0.91**(TP 10 · FP 1 · FN 1 · TN 2).

숫자를 그대로 쓰기 전에 알아야 할 것: **정상 평가 실험이 3개뿐**이라 precision이 그중
2개에 걸려 있다. 그래서 실험을 하나씩 빼며 다시 학습하는 leave-one-out 교차검증(LOOCV)도
같이 본다 — 11개 정상 실험 기준 9/11 양호, recall 평균 0.76. 발표·보고에는 이 두 숫자를
나란히 두는 걸 권한다. 원인은 순전히 데이터 양(사용 가능한 실험 22개)이고, 모델을
바꿔서 해결되는 문제가 아니다.

## D. 서빙 — `POST /predict`

CSV 업로드(multipart, `file` 필드) + `method`(mean/max/p95, 기본 mean)를 받아 판정 하나로
세 가지를 함께 낸다.

1. **판정** — `predicted_label`, `score`, `threshold`.
2. **원인 추정(`fault`)** — 불량이면 41개(랭킹은 셋업 상수 1개 제외 40개) 센서의 재구성
   오차를 z-score로 순위 매기고, 팀이 작성한 16개 상황 플레이북과 "관련 센서" 서명을
   대조한다. 순수 규칙 기반이라(임베딩·LLM 없음) 같은 입력이면 항상 같은 결과가 나온다.
   일치도에 따라 네 단계로 표기한다: `confirmed`(높은 패턴 일치) / `composite`(복합 패턴,
   다른 상황과 신호가 겹침) / `weak`(약한 신호, 보류 권고) / `unknown`(일치 패턴 없음) —
   화면·조치 문구에서는 "확정"이라는 단정적 표현을 쓰지 않는다(멘토 피드백 반영).
3. **조치 가이드(`guide`)** — `fault`가 잡히면 관련 문서 조각(팀 플레이북 + 외부 자료)을
   찾아 조치·안전 주의 문장을 생성한다. `confirmed` 등급에서만 외부 자료(Sandvik 밀링
   트러블슈팅) 검색에 임베딩을 쓴다. 정상 판정은 LLM 호출 없이 고정 문구를 낸다 —
   그래서 정상 판정은 항상 1초 안쪽이고, 불량 판정만 조치 문장 생성 때문에 몇 초 더 걸린다.

코드: [`src/serving/app.py`](../src/serving/app.py), [`src/rag/playbook.py`](../src/rag/playbook.py),
[`src/rag/guide.py`](../src/rag/guide.py).

## E. MLOps 인프라

- **실험 추적·레지스트리**: MLflow. 학습마다 run이 남고, 서빙이 쓰는 모델은 고정 버전
  번호가 아니라 `champion` alias로 가리킨다 — 승격은 alias만 바꾸면 되고 롤백도 즉시 된다.
- **동반 아티팩트 버전 결합**: `scaler.json`·`feature_baseline.json`을 모델과 같은 run에
  묶어 기록한다. 재학습이 이 파일들을 덮어쓰면 champion과 스케일이 어긋나 조용히 틀린
  추론을 하게 되는데, run 단위로 묶어 두면 그런 어긋남 자체가 생기지 않는다.
- **원자적 교체**: 승격은 "백업 → 파일 교체 → alias 교체 → 서빙 계약 검증" 순서로 하고,
  어느 단계든 실패하면 백업으로 되돌린다(`swap_with_rollback`). 모델(MLflow)과 동반
  파일(디스크)이 서로 다른 저장소에 있어서, 중간 실패를 롤백하지 않으면 짝이 어긋난
  채로 조용히 남기 때문이다.
- **설정 외부화**: 데이터 루트와 루프 상수(창 크기, 연속 트리거 횟수, 쿨다운 등)는
  `CNC_*` 환경변수로 바꿀 수 있다. 값이 잘못되면 조용히 기본값으로 떨어지지 않고
  import 시점에 죽는다 — 오타 하나가 40일짜리 루프를 엉뚱하게 돌리는 걸 막는다
  (`src/config.py`).

## F. 자동 재학습 루프

같은 드리프트 신호가 정반대 원인(계절·설비 변화로 재학습이 정답 / 설비가 실제로
고장 나는 중이라 재학습이 오답)에서 둘 다 나올 수 있다는 전제로 설계했다. 그래서
"트리거 → 재학습"에서 끝내지 않고 두 단계 검증을 더 거친다.

```
감지 → 트리거(연속 3회 + 쿨다운) → 재학습 → 두 방향 게이트 → 섀도우 → 승격 / 거부
```

- **감지**: 최근 10건 평균 판정 점수가 임계값의 0.8배를 넘거나(출력 드리프트), 입력
  피처 평균의 |z-score|가 2를 넘으면(입력 드리프트) 그 폴링을 "플래그"로 기록한다.
- **트리거**: 연속 3회 플래그 + 직전 재학습으로부터 쿨다운(기본 5일)이 끝났을 때만
  재학습을 발동한다. 쿨다운이 없으면 재학습 직후 남은 옛 로그 때문에 즉시 재발동한다.
- **재학습**: 그사이 도착한 정상 라벨 배치로 새 후보를 학습한다. 산출물은 격리된
  디렉터리에 두고, 게이트를 통과하기 전에는 정본(champion이 읽는 파일)을 건드리지 않는다.
- **두 방향 게이트**:
  - **G1(안전)** — 원래 평가셋 14개에서 불량 검출력이 champion 대비 유지되는가를
    **놓친 개수**로 비교한다(champion+1건까지 허용). recall 소수점 비교는 실험 1개당
    0.09씩 뚝뚝 끊겨 가짜 정밀도가 되므로 개수로 직접 비교한다.
  - **G2(근거)** — 라벨이 도착한 최근 구간에서 오탐과 놓침을 **따로** 세어, 어느 쪽도
    후퇴하지 않고 한쪽은 나아져야 통과시킨다. 이 구간에 정상 라벨이 하나도 없으면
    "오탐 회귀를 잴 수 없다"며 판정을 거부한다(통과가 아니라 거부) — 정확도 하나로만
    보면 창에 한 클래스만 있을 때 "무조건 불량이라고 하는" 후보가 이겨 버리는 사각지대가
    있었기 때문이다.
  - 둘 다 통과해야 다음 단계로 간다. 하나라도 실패하면 그 자리에서 거부다.
- **섀도우**: 게이트를 통과한 후보를 champion alias는 그대로 둔 채 실제 트래픽에
  병행 투입한다(응답에는 영향 없음, 기록만). 이후 생산분에서 정상 라벨 20건이 모이면
  champion과 한 번 더 비교해서 그때만 승격한다.
- **거부 시**: champion의 최근 기여도로 원인을 `tool_wear` / `vibration_backlash` 중
  하나로 추정하고, 그 카테고리 코퍼스로 조치 제안을 만들어 MLflow run 태그
  (`estimated_cause`, `recommended_action`)에 남긴다.

[`src/retraining/trigger.py`](../src/retraining/trigger.py),
[`src/retraining/gate.py`](../src/retraining/gate.py),

## G. 테스트·CI·실행
