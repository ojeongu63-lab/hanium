## 선택지를 제시하기 전에 맥락을 먼저 물을 것

**언제 (2026-08-14, 폴더 구조 정리)**

폴더 구조 정리 요청을 받고, 구조를 훑자마자 "정리 범위 A/B/C" 선택지를
제시했다. 사용자가 선택 대신 명확화를 요청했고, 그때 나온 답이 선택지의 전제를
바꿨다:

- **누가 읽는가** — 멘토·팀원 (외부 심사자가 아님)
- **CN7 트랙의 위상** — 접은 트랙. "방법론 먼저 검증하고 CNC로 넘어갔다"
- 이름 변경 가능 여부, 커밋 주체

이 넷을 모르는 상태에서 만든 선택지는 겉모습(파일을 얼마나 옮길지)만 다뤘고,
정작 중요한 것 — **어느 트랙이 메인인지 구조로 드러내는 일** — 은 다루지 못했다.
맥락을 듣고 나서야 "번호 접두사로 진행 순서를 표현"이라는 답이 나왔다.

**교훈:** 구조·문서·설계처럼 *독자가 있는* 산출물은, 선택지를 만들기 전에
**독자가 누구고 무엇을 알아야 하는지**부터 확인한다. 코드 구조는 읽어서 알 수
있지만 의도와 위상은 물어야만 안다.

## 이동 후 깨지는 것: venv shebang, DB 절대경로

**언제 (2026-08-14, 폴더 구조 정리)**

폴더를 옮길 때 "코드가 상대경로를 쓰니 안전하다"까지만 확인하면 부족했다.
실제로 깨진 곳:

- **`.venv/bin/*` shebang** — 옛 절대경로가 박혀 있다. `uv sync`는 `pyvenv.cfg`가
  유효하면 재생성을 건너뛰므로 안 고쳐진다. **venv는 옮기지 말고 지웠다 다시
  만든다.**
- **MLflow `mlflow.db`** — `artifact_location` / `artifact_uri` 등에 절대경로가
  저장된다.
- **스크립트의 `Path(__file__).parent.parent`** — 이름이 아니라 **깊이**에
  의존한다. rename은 안전하지만 depth 변경은 깨진다.

**교훈:** 이동 전에 `grep -rn "$(pwd)"` 로 **절대경로가 저장된 산출물**(venv,
sqlite DB, 캐시)을 먼저 찾는다. 소스 코드만 보면 놓친다.

## "단순한 방법이 먹힌다"는 결론은 규모를 키워서 다시 확인할 것

**언제 (2026-09-03, RAG 개선)**

사용자가 "시나리오 문서를 많이 써서 활용하면 되지 않나"라고 제안했고, 문서 4개를
더해 4/4가 맞자 "문서만 더하면 된다"고 답할 뻔했다. 사용자가 "너무 단순한 건
아닌지 체크해 달라"고 해서 상황을 16개(헷갈리는 항목 포함)로 늘리자 임베딩
검색은 2/4로 깨졌고, 1·2위 차이가 0.002였다. 4/4는 문서가 4개뿐이라 맞은
것이었다. 결국 임베딩 대신 문서에 적힌 센서 코드와 상위 피처를 대조하는 방식이
필요했고, 이건 타임라인 600건에서도 검증했다.

**교훈:** "이 정도면 된다"는 결론을 내기 전에, 데모에서 실제로 쓸 규모(문서 수·
상황 수·배치 수)로 키워서 같은 결과가 나오는지 본다. 작은 표본에서 맞는 방법은
표본이 작아서 맞은 것일 수 있다. 그리고 사용자가 "너무 단순하지 않냐"고 물으면
그건 검증 요청이다 — 안심시키지 말고 깨뜨려 본다.

## pkill -f 패턴은 그 명령 문자열을 담은 셸 자신과도 일치한다

**언제 (2026-09-02·09-03, 워커·서버 종료)**

`pkill -f 'drift_worker.py fixture_loosening'`, 그리고 서버 기동 줄과 같은 명령 안에
넣은 `pkill -f '[u]vicorn serving.app'`이 두 번 다 제 셸을 먼저 죽였다(exit 144).
대괄호 트릭은 pkill 줄 자체는 피하지만, 같은 명령 문자열에 `uvicorn serving.app:app`
같은 기동 줄이 있으면 셸의 명령줄이 패턴과 일치한다.

**교훈:** 프로세스 종료는 PID 파일(`kill $(cat x.pid)`)로 하고, 패턴 kill이 필요하면
기동 줄이 없는 **별도 명령**에서만 한다. 한 명령에 "띄우고 죽이기"를 같이 넣지 않는다.

## 계획서에 적힌 테스트 코드도 돌려 보기 전엔 가설이다

**언제 (2026-09-18, 루프 통합 테스트 Task 8·9)**

계획서에 테스트 코드를 전문으로 적어 두고 구현 때 그대로 옮겼다. MLflow
3.14의 SQL 저장소는 모델 버전을 int로 돌려주는데 계획의 단언은 문자열
`"1"`과 비교했다. 승격 테스트의 `champion != "1"`은 절대 실패할 수 없는
공허한 단언이었고, 거부 테스트의 `... .version == "1"`은 매번 실패했다.
둘 다 계획을 쓸 때 한 번도 돌려 보지 않은 코드였다. 구현 때 계획의
테스트를 먼저 그대로 돌려 본 단계(RED 확인)에서 드러났다.

**교훈:** 계획서 속 테스트 코드는 명세가 아니라 가설이다. 옮긴 뒤 한 번은
실제로 돌려, 실패해야 할 때 실패하는지(공허한 단언이 아닌지)부터 본다.
외부 라이브러리가 돌려주는 값은 타입까지 확인한다.

## 반환값의 개수·형태를 바꾸면 모든 호출부를 grep한다

**언제 (2026-09-18, 루프 통합 테스트 Task 7)**

09-03(6b5f12b)에 `load_rag_state()`가 3-튜플에서 4-튜플이 됐다. 같은
커밋에서 서버 쪽 호출부는 고쳤지만 `drift_worker.main()`은 3개로 언패킹한
채 남아, 독립 실행 워커가 시작하자마자 `ValueError`로 죽었다. 단위 테스트는
`main()`을 돌리지 않아 전부 통과했고, 그 뒤로 아무도 워커를 띄우지 않아
2주 동안 몰랐다. 통합 테스트 하네스가 워커를 실제 프로세스로 띄운 첫
실행에서 드러났다.

**교훈:** 함수의 반환 형태를 바꾸면 `grep -rn "함수명("`으로 스크립트
진입점까지 모든 호출부를 찾아 같이 고친다. 단위 테스트가 닿지 않는
진입점(`main()`)은 한 번은 실제로 띄워 본다.
