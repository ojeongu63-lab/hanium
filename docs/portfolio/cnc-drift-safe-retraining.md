# 불량 라벨이 없는 CNC 공정에서, 드리프트 신호를 믿지 않고 검증한 뒤 재학습하는 루프

**한이음 프로젝트 · AI&데이터 파트 (2026-07 ~ 2026-10)** — 데이터 전처리, 이상탐지 모델, 서빙, 드리프트 감지·재학습·승격 루프를
혼자 담당. Python · PyTorch · MLflow · FastAPI · SQLite · GitHub Actions · Docker Compose.
저장소의 설계서 19개와 실행 기록(`docs/specs/` — 실행을 동반한 설계서에 붙인 "실행 결과에 따른 정정" 절, 작업 일지)이 이 글의 출처다.

> **한 줄 요약.** 같은 "드리프트" 신호가 *계절 변화(재학습이 정답)*와 *설비 고장(재학습이 오답)*에서 똑같이 나온다.
> 그래서 "드리프트 → 재학습"이 아니라 **"트리거 → 재학습 → 두 방향 게이트 → 섀도우 → 승격 또는 거부"** 루프를 만들고,
> 실제 CNC 센서 데이터 위에 합성한 40~70일 운영 타임라인 3종으로 승격 경로와 거부 경로를 끝까지 검증했다.

**핵심 결과**

- 온도 드리프트(제품 정상): 재학습이 **세 번 거부된 뒤 네 번째에 승격** — 라벨이 7일 늦게 오므로 "교체할 근거"가 그때야 생겼다. 승격 뒤 점수/임계값 비율 1.76 → 1.09(오탐 소멸).
- 공구 마모·고정구 풀림(실제 불량): 재학습 **10회 전부 거부**, champion 유지, 거부 10건 모두 원인 추정 정답. 그중 단일 클래스 창에서 "더 자주 불량이라 하는" 후보가 통과해 버리는 **게이트 사각지대를 실측에서 찾아 재설계**했다.
- 루프 전체가 서버·워커 서브프로세스 통합 테스트로 CI에서 매번 돌고, 라이브로는 8분 안에 승격까지 재현된다.

## 1. 현장에서 출발한 문제

**불량 라벨은 거의 없고, 있어도 늦게 온다.** 제조 현장은 불량 샘플을 모아 분류기를 만들 만큼 라벨이 없다. 그래서 정상
데이터만으로 학습한 LSTM-Autoencoder의 재구성 오차로 "평소와 다른 패턴"을 잡고, 임계값도 정상 실험 8개의 오차 분포에서만
정했다(평가 라벨은 임계값 결정에 관여하지 않는다). QC 라벨은 생산 뒤 며칠 지나서 도착한다 — 시뮬레이션에도 **라벨 지연 7일**을
그대로 넣었다.

**멘토의 요구는 "드리프트가 감지되면 자동으로 재학습되는 것까지"였다.** 드리프트 감지(요청 누적, 입력 z-score·출력
점수 비율, `/drift-status`)는 이미 있었다. 문제는 감지 *이후*였다. 시간이 지나 입력 분포가 움직이면 모델이 배운 "정상의
정의"가 낡아 오탐이 늘고, 이때 필요한 건 설비 정비가 아니라 정상 기준의 갱신, 즉 재학습이다.

**그런데 같은 신호가 정반대 원인에서 나온다.**

| 상황 | 입력 분포 | 제품 품질 | 모델 판단 | 올바른 처방 |
|---|---|---|---|---|
| 계절·온도 변화 | 이동 | 정상 | 오탐 | **재학습** |
| 설비 노후화 (초기) | 이동 | 아직 QC 합격 | 오탐 | 재학습해도 규칙 위반은 아니나 **위험** |
| 설비 노후화 (진행) | 이동 | 불량 | 정탐 | **정비 — 재학습 금지** |

드리프트 지표만으로는 셋을 구분할 수 없다. 구분에 필요한 것은 원인이 아니라 "제품이 실제로 불량이냐"인데, 그 정보(QC 라벨)는
항상 늦게 온다. 세 번째 행에서 재학습하면 모델에게 불량을 정상이라고 가르치는 셈이고, 더 까다로운 두 번째 행은 QC를 통과한
데이터라 재학습에 넣어도 규칙 위반이 아니지만, 계속 넣으면 **정상 기준이 열화를 따라 조금씩 내려간다.**

그래서 구조를 "트리거 → 재학습"이 아니라 **"트리거 → 재학습 → 게이트 → 승격 또는 거부"**로 잡았다. 직전 설계(드리프트
모니터링)에서 자동 승격을 비목표로 뒀던 이유가 바로 "게이트 없는 자동 재학습은 위험하다"였고, 그 결정을 뒤집을 수 있었던
근거는 게이트를 함께 만들기 때문이었다.

## 2. 현장 제약을 설계로 옮긴 결정들

| 결정 | 현장 이유 | 근거·실측 |
|---|---|---|
| 정상만 학습, 임계값은 정상 8개의 오차 p95 | 불량 라벨이 없다는 전제를 지킨다 | 평가 실험 14개 precision 0.91 / recall 0.91, 정상 평가가 3개뿐임을 명시하고 LOOCV(정상 11개 중 9개 양호) 병기 |
| 데이터에 시간축이 없어 **가상 운영 타임라인**을 합성 | "시간이 지나며 나빠진다"를 보이려면 순서가 있어야 한다 | TimeGAN(표본 부족)·물리 시뮬레이션(별도 프로젝트 규모)을 기각하고, 실험 8개에 날짜 비례 변형을 주입. 변형 폭은 실제 불량 실험의 점수/임계값 대역(1.0~3.8) 안에 가둠 |
| 트리거 = 연속 3회 flagged + 쿨다운 5일 | 재학습 직후 남은 옛 요청 로그로 즉시 재발동하는 것을 막는다 | 섀도우 기간이 쿨다운보다 길어 승격 직후 재트리거되는 문제를 실측에서 발견, 섀도우 종료 시에도 쿨다운 재설정 |
| **G1(안전)**: 원본 평가셋에서 놓친 불량 개수 ≤ champion + 1 | 열화를 정상으로 배운 모델을 막는다 | 처음엔 `recall ≥ champion − 0.10`이었으나 불량 11개라 눈금이 0.09 — 소수점은 가짜 정밀도라 **개수**로 바꿈. precision은 재학습 scaler의 좌표계 이동 영향이라 제외 |
| **G2(근거)**: 라벨이 도착한 최근 20건에서 오탐·놓침을 **따로** 비교 | "지금 현장에서 더 나은가"만 묻는다 | 정확도 하나로 비교하던 규칙이 단일 클래스 창에서 뚫리는 것을 실측(§3) → 클래스별 회귀 금지, 정상 라벨이 없는 창은 "판정 불가"로 거부 |
| **섀도우**: 게이트 통과 후보를 champion alias는 그대로 둔 채 실트래픽에 병행 투입, 이후 생산분 라벨 20건으로 재비교 | 게이트는 과거 구간의 사후 재현이라 미래에도 나은지는 모른다 | 70일 재현에서 시작 → 실시간 관찰 → 라벨 매칭 → 승격까지 작동(v1 → v63) |
| 승격은 **백업 → 계약 확인 → 파일 교체 → alias 교체 → 리로드 → 검증**, 중간 실패 시 롤백 | 모델(MLflow)과 동반 파일(디스크)이 다른 저장소라 중간에 실패하면 짝이 어긋난다 | 계약 확인을 파일 교체 *앞에* 둬 롤백할 일 자체를 줄임. 거부 5회 뒤 정본 해시 불변 확인 |
| scaler·feature_baseline을 모델과 같은 run에 결합 | 재학습이 이 파일을 덮어쓰면 champion과 스케일이 어긋난 채 조용히 틀린다 | 수동 승격에서는 안 드러나고 자동 루프에서 즉시 터진 결함. alias만 되돌렸다가 디스크 파일은 v5 것이 남는 사고를 겪고 백업 복원까지 묶음 |
| 서빙·감시 워커·feeder를 **별도 프로세스**로 | 재학습(수십 초~2분)이 추론 응답을 막으면 라인이 선다 | `/predict`가 동기 추론으로 이벤트 루프를 막아 `/health`가 3.9초 대기하던 것을 실측 → 수정 후 0.004초 |
| 거부하면 원인을 `tool_wear` / `vibration_backlash`로 추정하고 조치 제안을 MLflow 태그로 | 운영자는 "거부됨"이 아니라 무엇을 봐야 하는지를 알아야 한다 | 두 차례 라이브 재현의 거부 18건(8/8, 10/10) 전부 정답 카테고리, 반대쪽으로 넘어간 적 없음 |
| 설정값은 환경변수로, 잘못된 값은 조용히 기본값으로 떨어지지 않고 시작 시 죽음 | 오타 하나가 40일짜리 루프를 엉뚱하게 돌린다 | `src/config.py` |
| 원하는 결과가 나올 때까지 값을 돌리지 않는다 | 데모가 성립하도록 맞추는 순간 검증이 아니다 | 평가 창 30~40 절충, 임계값 통계량 교체를 모두 하지 않고 한계로 기록(§4) |

## 3. 실제 센서 데이터 위에서 돌려 본 결과

세 시나리오 모두 실제 KAMP CNC 밀링 실험 CSV(컨트롤러 샘플링 tick 단위, 41채널)를 baseline으로 쓰고, 변형만 날짜에 비례해 주입했다.
서빙·워커·feeder를 실제 프로세스 3개로 띄운 라이브 실행이며, 수치는 워커 로그와 MLflow 태그에서 가져왔다.

### 3-1. 온도·계절 드리프트 — 제품은 정상, 재학습이 정답 (승격 경로)

| 트리거 | G1 (놓침, 허용 champion+1) | G2 (후보 vs champion) | 판정 |
|---|---|---|---|
| Day 22 | 0건 ✓ | 0.65 vs 0.90 | 거부 |
| Day 27 | 0건 ✓ | 0.65 vs 0.90 | 거부 |
| Day 32 | 0건 ✓ | 0.45 vs 0.60 | 거부 |
| **Day 37** | 0건 ✓ | **0.45 vs 0.10** | **승격** |

계획 때는 "트리거 → 바로 승격"을 예상했는데 세 번 거부됐다. 원인은 라벨 지연 7일이다 — Day 22에 도착한 라벨은 Day 15까지인데
그 구간은 드리프트가 약해 champion이 아직 잘 하고 있었다(0.90). **champion을 바꿔야 한다는 증거가 라벨에 아직 없었다.**
Day 32에 champion이 0.60으로 떨어지고 Day 37에 0.10까지 무너지면서야 승격됐다. 드리프트 지표는 Day 17부터 울렸지만 모델을
교체할 근거는 Day 37에야 생겼다 — **자동화는 신호가 울리자마자 조치하는 게 아니라 근거가 쌓일 때까지 기다릴 줄 알아야
한다**는 것을 게이트가 스스로 보여 준 장면이다. 승격 뒤 점수/임계값 비율은 1.76 → 1.12 → 1.09로 내려가 오탐이 사라졌다.

### 3-2. 공구 마모 — 실제 불량, 재학습이 오답 (거부 경로)

5회 트리거(Day 19·24·29·34·39) **모두 거부**, champion v1 유지, 정본 파일 해시 불변. 재학습 모델은 갈수록 나빠졌다
(G2 0.90 → 0.40). 설계 때는 "원본 평가셋의 불량을 놓쳐 G1이 막는다"고 예상했는데 **실제로는 G2가 막았다**: 재학습은
scaler를 새로 fit하므로 원본 평가셋 전체가 낯선 좌표계로 옮겨져 거의 전부 불량으로 판정되고 recall이 자동으로 1.0이
된다. 예측한 둔감화는 실재했고(전부 불량인 창 20건 중 8건만 잡음, champion은 20건) G2에서 드러났다. G1을 단독 방어선으로
뒀다면 이 시나리오는 승격됐을 것이다 — 예측 메커니즘은 틀렸고 결과는 맞았으며, 둘 다 그대로 기록했다.

### 3-3. 고정구 풀림 — 게이트의 사각지대를 찾아 재설계

4번째 재학습(Day 34)이 게이트를 **통과해 버렸다.** 그 시점 G2 창(생산일 24~27)은 불량 시작(Day 21) + 라벨 지연(7일) 때문에
정답이 전부 불량이었다. 후보를 champion과 같은 배치에 다시 돌려 보니:

| 창 | champion | 후보 |
|---|---|---|
| 전부 불량인 Day 24~27 | 12/20 | 16/20 → 통과 |
| 전부 정상인 Day 14~17 | 17/20 (오탐 3) | 11/20 (오탐 9) |

후보는 배치 순위가 champion과 같고 임계값만 낮았다(0.62 vs 0.86) — 무엇을 더 잘 구분하는 게 아니라 **더 자주 불량이라
하는 모델**이고, 승격됐다면 정상 제품의 오경보가 3배가 됐을 것이다. 정확도 하나로 비교하면 창에 한 클래스만 있을 때
과탐이 "개선"으로 읽힌다. 그래서 G2를 **오탐과 놓침을 따로 세고, 한쪽을 다른 쪽과 맞바꾸는 후보와 정상 라벨이 없는 창을
통과시키지 않는** 두 방향 규칙으로 바꿨다(구현 전에 보관해 둔 후보 9개에 새 규칙을 사후 적용해 뒤집히는 것이 그 창 하나뿐임을
먼저 확인했다). 재실행 결과:

| 시나리오 (40일) | 트리거 | 새 규칙 | 기존 규칙이었다면 |
|---|---|---|---|
| 고정구 풀림 | 5회 | **5회 모두 거부** (오탐 회귀 2, 맞바꾸기 1, 정상 라벨 없음 2) | Day 30·35 **2회 통과** |
| 공구 마모 | 5회 | **5회 모두 거부** (개선 없음 1, 오탐 회귀 1, 맞바꾸기 1, 정상 라벨 없음 2) | 5회 거부 (그중 2회는 동률이라 우연) |
| 온도 (70일) | 4회 + 승격 후 1회 | 거부 3회 → Day 37 통과 → 섀도우 → **Day 64 승격 (v63)** | 동일 — 정상 라벨뿐인 창에서는 두 규칙이 수학적으로 같다 |

네 가지 거부 사유가 전부 실제로 나왔고, 거부 10건 모두 원인 추정·조치 제안·MLflow 태그가 남았다.

### 3-4. 평가 창을 넓히면 구모델이 유리해진다 — 손잡이를 돌리지 않은 이유

G2 표본을 20건에서 60건으로 넓혀 봤더니 **온도 시나리오의 승격이 거부로 뒤집혔다**(Day 37: 후보 0.45 vs champion 0.10 →
0.48 vs 0.50). 창을 과거로 넓히면 재학습 모델이 강한 최근 구간이 희석되고 champion은 자기가 잘하던 옛 구간 점수를
벌어들인다. 드리프트 상황에서 평가 창 확대는 중립이 아니라 구모델에 유리하다. 20으로 되돌렸고, 30~40으로 절충해 승격이
살아나는지 보는 일은 하지 않았다 — 원하는 결과가 나올 때까지 손잡이를 돌리는 행위이기 때문이다. 대신 "창 크기가 판정을
뒤집을 만큼 민감하다"를 알려진 한계로 적었다.

### 3-5. 라이브 시연

루프 상수(`CNC_*`)를 화면용으로 줄이면 같은 코드가 **8분 안에** 한 바퀴 돈다(2026-10-21 리허설: Day 4~6 flagged → Day 6
트리거·재학습 23초·게이트 통과·섀도우 → Day 8 승격 → Day 9 새 champion으로 정상 판정, 7분 47초). 실행 절차는
[`docs/시연자료_202610/README.md`](../시연자료_202610/README.md).

## 4. 정직하게 적어 두는 한계

- **데이터 양.** 사용 가능한 실험 22개(학습 8 · 정상 평가 3 · 불량 평가 11). 정상 평가가 3개라 precision은 2개에 걸려 있고,
  LOOCV로는 정상 11개 중 9개 양호. 모델을 바꿔서 풀리는 문제가 아니다. 합성 데이터로 평가셋을 채우지는 않았다 — 게이트가
  자기가 만든 답을 채점하게 되기 때문이다.
- **실험 사이에 시간축이 없다.** 드리프트는 우리가 주입한 변형이다. 루프와 판정 규칙의 검증이지, 실제 현장의 드리프트가 그런
  모양으로 온다는 증거는 아니다. 온도 시나리오의 열변위 방향은 데이터에 온도 기록이 없어 실측 근거가 없는 판단이다.
- **G1은 실측에서 한 번도 작동하지 않았다.** 재학습 scaler의 좌표계 효과가 놓침 신호를 묻는다. 안전의 본체는 G2다.
- **평가 창 크기에 민감하다**(§3-4). 창 20건의 구성이 원본 실험 8개의 순환 순서에 좌우된다.
- **재학습 후보의 임계값은 학습 오차 기준이라 데이터가 늘수록 과민해진다.** 홀드아웃 보정을 실제로 세 지점에서 시제품으로
  돌려 봤으나, 특정 조건(feedrate 20)의 정상 실험이 p95를 끌어올려 후보가 반대쪽으로 둔해졌다. 보류하고 기록했다.
- **워커 로그의 "Day N"은 스냅샷이 아니다.** `/drift-status`는 최근 요청 10건을 보므로 feeder가 앞서 가면 그 시점 값이 아니다.
  게이트는 두 모델을 직접 돌려 비교하므로 영향이 없고, 트리거 타이밍만 하루쯤 흔들릴 수 있다.
- **운영 관측 계층이 없다.** 들어오는 데이터와 실시간 점수·루프 이벤트를 한 화면에서 보는 대시보드는 아직 없다(§6).

## 5. MLOps 공학

- **레지스트리·승격.** MLflow `champion` alias로 서빙이 모델을 집고, 승격은 alias 교체 + 동반 파일 교체 + `/reload-model`.
  실데이터 리허설로 생긴 재학습 run 63개(v2~v64)가 거부·승격 사유 태그와 함께 레지스트리에 남아 있다.
- **검증.** 단위 테스트 229개. 루프 통합 테스트 3개는 서버·워커를 실제 서브프로세스로 띄우고 합성 데이터셋으로 champion을
  만들어 트리거 → 재학습 → 게이트 → 섀도우 → 승격 / 거부 경로를 끝까지 확인한다(실데이터 불필요, 약 150초). 하네스가
  단위 테스트로는 안 잡히던 버그 2건(독립 실행 워커의 튜플 언패킹, feeder의 라벨 기록 타이밍)을 찾았다.
- **CI.** GitHub Actions 3 job(단위 · 루프 통합 · `docker compose build`), main push마다 실행, 세 job 모두 실제 green 확인.
- **실행.** `docker compose --profile demo up` 한 줄로 서빙 + 워커 + feeder. 데이터 루트와 루프 상수는 전부 환경변수.
- **기록.** 설계서 19개. 실행을 동반한 설계서(재학습 루프·섀도우·원인 추정·두 방향 게이트·통합 테스트 등)에는 "실행 결과에 따른
  정정" 절을 두어, 계획과 실측이 다를 때 값을 고친 게 아니라 다른 점을 적었다.

## 6. 다음

1. **실시간 관측 계층** — 실험 CSV를 원본 샘플링 주기의 행 단위로 재생하는 수집기, 20-tick 창마다 champion으로 점수를 내는 슬라이딩
   윈도우 실시간 추론, 센서 파형·창 점수·드리프트·모델 버전·루프 이벤트를 서버 푸시로 보여 주는 라이브 대시보드. 판정과
   루프는 지금처럼 작업 단위로 집계해 워커를 그대로 쓴다.
2. **실제 시간축이 있는 데이터** — 다기간·다기계로 수집된 공개 CNC 진동 데이터(Bosch CNC Machining)를 두 번째 기계로 붙여,
   주입이 아닌 실제 드리프트에서 트리거·게이트가 어떻게 동작하는지 본다.
3. **임계값 보정** — 보류한 홀드아웃 보정을 조건별 정상 표본이 더 확보되면 다시 본다.
