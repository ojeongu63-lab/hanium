# CNC 데이터셋 전처리 파이프라인 설계

- 날짜: 2026-07-24
- 상태: 설계 완료, 구현 전

## 배경

CN7 사출성형 데이터로 준지도 LSTM 오토인코더 이상탐지를 구현했으나, 평가셋의 진짜 불량이
18건뿐이라 precision/recall의 통계적 신뢰도가 낮았다(`hanium/01-cn7-injection-molding/docs/specs/2026-07-22-cn7-lstm-autoencoder-design.md`
참고). 이 방법론이 CN7이라는 특정 데이터셋의 한계 때문에 나쁘게 나온 것인지, 아니면 방법론
자체의 한계인지 객관적으로 판단하기 위해 KAMP의 다른 제조 데이터셋(CNC 머신 AI 데이터셋)에
같은 방법론을 적용해본다.

CNC 데이터셋은 자동차 부품 CNC 가공 공정에서 절삭공구 마모에 따른 가공불량을 예측하는 것이
목적이며, `02-cnc-machining/data/` 아래에 배치되었다. 원 가이드북(`03. Guidebook_CNC_데이터부분.pdf`)은
지도학습 DNN 분류 데모를 다루지만, 이 프로젝트는 CN7과 동일하게 **준지도 이상탐지(재구성오차 →
변수별 오차로 설명 → 향후 RAG 매칭)** 를 주 트랙으로 삼고, 이 데이터셋은 라벨이 CN7보다 훨씬
균형 잡혀 있다는 특성을 살려 **지도학습 분류기를 보조 비교군**으로 추가한다(사용자 확인 완료).
이 스펙은 두 트랙이 공통으로 쓸 train/eval 데이터를 만드는 전처리 단계만 다룬다. 모델링(LSTM-AE,
지도학습 분류기)은 각각 별도 스펙에서 다룬다.

**환경 제약**: CN7과 동일하게 GPU 없는 CPU 전용 서버.

## 목표 / 비목표

**목표**
- `train.csv`(25개 실험 메타데이터) + `experiment_01~25.csv`(실험별 초단위 원본 로그)만을
  입력으로 삼아, 실험 단위로 리키지 없이 나뉜 train/eval 데이터셋을 만든다.
- 죽은 컬럼(상시 0)을 실측으로 확인해 제거한다.
- 준지도 트랙(LSTM-AE)과 지도학습 트랙(분류기)이 동일한 train/eval/피처 정의를 공유하게 해서
  두 트랙의 결과가 직접 비교 가능하게 한다.

**비목표 (다음 스펙에서 다룸)**
- LSTM-AE, 지도학습 분류기의 모델 아키텍처/학습 설계
- RAG 불량유형 매칭
- `feedrate`/`clamp_pressure` 등 실험 조건 자체의 인과관계 분석

## 데이터 계보 (조사 결과 요약)

`02-cnc-machining/data/dataset/`에 두 폴더가 있다:

- **`CNC 비식별화 원본데이터_1209`** (원본, 이 스펙의 입력): `train.csv`(25개 실험의 조건/결과
  메타데이터) + `CNC Virtual Data set _v2/experiment_01~25.csv`(실험별 1초 주기 센서 로그,
  실험당 462~2333행, 48개 컬럼).
- **`CNC 학습통합데이터_1209`** (KAMP가 미리 만든 2차가공 X/Y train/test): **사용하지 않는다.**
  직접 검증한 결과, `Y_train`은 정확히 앞 9,403행이 양품·뒤 9,403행이 불량인 완벽한 50/50
  블록이고, `Y_test`는 13,242행 전부가 양품이었다. 산술로 재확인: 불량 총 9,403행(경계 실험
  없이 정확히 일치)이 전부 train에, 양품 22,645행 중 9,403행만 train에(균형용) 나머지
  13,242행은 전부 test에 들어간 것 — **test셋에 불량 샘플이 0건**이라 held-out 평가셋으로 쓸
  수 없다. CN7 때 KAMP의 스케일링된 2차가공 파일 대신 원본을 직접 재가공했던 것과 같은 이유로,
  여기서도 원본만 사용한다.

## 라벨 정의

`train.csv`의 실험별 조건: `No, material, feedrate, clamp_pressure`(입력) /
`tool_condition, machining_finalized, passed_visual_inspection`(결과).

양품(label=0) = `machining_finalized=='yes'` AND `passed_visual_inspection=='yes'`.
나머지(미완료, 또는 완료됐지만 검사 불합격)는 전부 불량(label=1). 이 라벨은 실험 단위로
정해지며, 그 실험의 모든 행(초 단위 샘플)에 동일하게 상속한다.

전체 25개 실험 중 **양품 13개(22,645행), 불량 12개(9,403행)** — 총 32,048행. `tool_condition`은
라벨이 아니라 실험 설계 변수(마모된 공구/새 공구를 일부러 나눠 실험)이며, 마모된 공구로도
양품이 나온 경우가 다수 있어 `tool_condition`과 양품/불량이 1:1로 대응하지 않는다.

## 컬럼 정제 (실측 확인됨)

원본 25개 실험 전체(32,048행)를 직접 확인한 결과, 4개 컬럼이 전 구간에서 상시 0이었다:
`Z_CurrentFeedback`, `Z_DCBusVoltage`, `Z_OutputCurrent`, `Z_OutputVoltage` — 드롭한다.
(가이드북 자체 기술통계표에도 이 4개가 0으로 나와 있으나, 그 표는 문제가 있는 KAMP
2차가공 X_train 기준이라 원본 전체로 재확인함. 결과는 일치했다.)

`Machining_Process`(가공 단계 범주값)에 `"End"`(3,207행)와 `"end"`(8행)가 대소문자만 다르게
섞여 있다 — `"End"`로 통일한다. 그 외 결측치는 없다(48개 센서 컬럼 전 구간 확인).

남은 44개 컬럼 중 아래 3개는 물리 센서값이 아니라 프로그램 상태/인덱스 성격이라 **모델
피처에서 제외하고 메타데이터로만 보존**한다(CN7이 `TimeStamp`/`Reason`을 피처에서 뺀 것과
같은 원칙):
- `M_CURRENT_PROGRAM_NUMBER`(실행 중 프로그램 번호), `M_sequence_number`(G-code 라인 번호) —
  사실상 프로그램 내 위치 인덱스, 시퀀스 순서로 이미 암묵적으로 드러남.
- `Machining_Process` — 범주값. 가공 단계별로 정상 범위가 크게 다를 수 있어 유용한 정보지만,
  이번 1차 비교에서는 CN7과 동일하게 "연속 센서값만 입력"으로 단순하게 가고, 결과가 나쁘면
  피처로 재검토한다(단순성 우선, 미리 복잡도를 넣지 않음).

`M_CURRENT_FEEDRATE`(순간 공급속도)는 연속 물리량이라 피처로 유지한다.

**최종 `FEATURE_COLUMNS` = 41개**: X축 11개(전부) + Y축 11개(전부) + Z축 6개(죽은 4개 제외) +
스핀들(S) 12개(전부) + `M_CURRENT_FEEDRATE` 1개.

## Train / Eval 분할 (실험 단위)

행 단위가 아니라 **실험 단위**로 통째로 나눈다 — KAMP의 2차가공 데이터가 실험 하나를 중간에
잘라 train/test에 걸치게 한 것과 같은 실수를 피하기 위함이다. `feedrate`(3/6/12/15/20),
`clamp_pressure`(2.5/3/4), `tool_condition`(worn/unworn) 조합이 train에도 최대한 골고루
남도록 양품 13개 중 8개를 수동으로 선정했다:

| 구분 | 실험 번호 | 개수 | 행수 |
|---|---|---|---|
| Train (양품만) | 1, 2, 3, 11, 13, 14, 15, 17 | 8 | 14,654 |
| Eval — 양품 | 12, 18, 22, 24, 25 | 5 | 7,991 |
| Eval — 불량 | 4, 5, 6, 7, 8, 9, 10, 16, 19, 20, 21, 23 | 12 | 9,403 |

**(사후 보정됨 — 아래 "사후 보정" 절 참고)**: 실험 19/24/25가 원본 데이터 자체의 중복임이
LSTM-AE 모델링 단계에서 드러나 최종적으로 제외됐다. 이 표는 최초 설계 당시의 분할이며,
실제 채택된 최종 분할은 문서 끝 "사후 보정" 절 참고.

Train은 `feedrate` {3,6,20}, `clamp_pressure` {2.5,3,4}, `tool_condition`(unworn 5 /
worn 3) 조합을 모두 포함한다. Eval도 양품 5개(unworn 2 / worn 3)로 다시 한 번 여러 조건을
포함한다. 불량 12개는 전부 eval에 둔다(CN7이 알려진 불량 18건 전부를 eval에 둔 것과 동일).

**Eval 데이터셋 구성**: 총 17,394행 중 양품 7,991 / 불량 9,403(54.1%) — CN7 eval(불량 0.45%)
대비 클래스 균형이 훨씬 좋다. 이 데이터셋이 CN7보다 통계적으로 신뢰할 만한 precision/recall을
줄 수 있을지는 이 균형 덕분에 검증 가능해진다.

Train(14,654행)은 전부 label=0(양품)이다 — 준지도 트랙은 이 label 컬럼을 무시하고 "정상"으로만
사용하고, 지도학습 트랙은 eval 쪽 라벨과 함께 별도 스펙에서 어떻게 학습셋을 구성할지 정한다
(이 스펙은 공통 train/eval 파일만 만든다).

## 그 외 전처리 결정

- **자가정제(IsolationForest) 생략**: CN7의 train(unlabeled)은 라벨이 전혀 없어 자가정제로
  명백한 이상치를 걸러내야 했지만, 여기 train은 이미 확정된 양품 라벨이라 불필요한 복잡도를
  추가하지 않는다.
- **드리프트 보정(rolling z-score) 생략**: CN7은 train(대략 2020-03-24~10-20)과 eval
  (2020-10-16~11-03)의 시간 범위가 거의 겹치지 않아 공정 드리프트가 있었다. CNC는 25개 실험
  전부 2020-10-19~10-23 5일 안에 수집돼 그런 큰 시간 격차가 없으므로 넣지 않는다. 다만 이건
  가정이며, 모델링 스펙에서 실제로 재구성오차가 실험 순서/시간에 따라 이상하게 흔들리는지
  확인해서 필요하면 그때 추가한다(CN7도 드리프트 보정을 사후에 추가했던 전례를 따름).
- **스케일링**: `StandardScaler`를 train(8개 양품 실험, 14,654행)에만 `fit`하고, train/eval
  모두 동일한 스케일러로 `transform`한다(eval 재fit 없음 — 리키지 방지). 컬럼별 mean/std는
  `scaler.json`에 저장한다.

## 출력 (`02-cnc-machining/data/processed/`)

| 파일 | 내용 |
|---|---|
| `train.csv` | 41개 피처(스케일링됨) + `experiment_id` — 14,654행, 전부 label=0 |
| `eval.csv` | 41개 피처(스케일링됨) + `experiment_id`, `label`, `tool_condition`, `feedrate`, `clamp_pressure`, `material`, `Machining_Process`, `M_sequence_number`, `M_CURRENT_PROGRAM_NUMBER` — 17,394행 |

`eval.csv`에 `tool_condition`/`feedrate`/`clamp_pressure`/`Machining_Process` 등을 메타데이터로
남기는 이유: 모델 피처에서는 뺐지만, 나중에 "왜 이 실험이 불량으로 판정됐는가"를 설명하거나
RAG 매칭 근거로 쓸 때 필요하기 때문이다(CN7이 `eval.csv`에 `Reason`/`TimeStamp`를 남긴 것과
같은 이유).

## 알려진 한계 / 리스크

- 양품 13개 중 8개만 train에 써서 학습 데이터가 CN7(16,908행)보다 적다(14,654행이지만 실험
  조건 다양성은 CN7보다 낮음 — 8개 실험 조합뿐).
- `feedrate`=12, 15는 양품 실험에 아예 없다(전부 불량 실험에서만 등장) — train이 이 두
  feedrate 구간을 전혀 학습하지 못한 채 eval에서 마주치므로, 모델이 이 구간에서 오탐을 낼
  위험이 구조적으로 존재한다. 결과 해석 시 감안해야 한다.
- 실험 25개(양품 13/불량 12)라는 표본 크기 자체가 작아, 지도학습 분류기가 아주 잘 나오더라도
  일반화 여부를 확신하기는 어렵다.
- `material`은 25개 실험 전부 `aluminum`으로 고정이라 변별력이 없다(참고용으로만 보존).

## 사후 보정 (2026-07-24, LSTM-AE 모델링 결과 리뷰 중 발견)

이 스펙 설계·구현 당시에는 몰랐다가, LSTM-AE 학습·평가 결과를 최종 리뷰하는 과정에서
결과가 CN7보다 유독 좋게 나온 이유를 검증하다가 발견한 문제를 반영했다.

**발견**: 원본 `experiment_XX.csv` 25개 전체를 `md5sum`으로 직접 대조한 결과, 정확히 2개
쌍이 완전히 동일한 파일이었다(그 외 중복 없음):
- **실험14(train) == 실험24(eval-양품)**: 센서 데이터 전 행이 완전히 동일(md5 일치, 2333행).
  `train.csv`의 메타데이터상 `tool_condition`만 다르게(worn/unworn) 기록돼 있으나 센서값이
  같으므로 둘 중 하나는 메타데이터 오류로 보인다. 라벨(양품)은 둘 다 같아 라벨 모순은 없지만,
  같은 실험이 train과 eval에 동시에 들어가는 **리키지**였다.
- **실험19(eval-불량) == 실험25(eval-양품)**: 센서 데이터가 완전히 동일한데(566행)
  `feedrate`/`clamp_pressure`/양품판정이 전부 다르게 기록돼 있다 — 물리적으로 같은 기록이
  서로 다른 결과로 라벨링된 것이라 **어느 쪽 라벨도 신뢰할 수 없다**.

CN7의 82% 완전 중복행 발견과 같은 성격의 원본 데이터 자체의 결함이며, 우리 전처리 로직의
버그가 아니다(원본 파일 자체가 이미 동일함).

**반영**: `EXCLUDED_DUPLICATE_EXPERIMENT_IDS = [19, 24, 25]`를 신설해 세 실험을 전부
제외했다(실험14는 train에 그대로 유지 — 최초 설계의 조건 다양성을 보존하기 위해 24 쪽을
제외). 19/25는 라벨을 신뢰할 수 없어 둘 다 제외.

**최종 분할 (25개 중 22개 사용)**:

| 구분 | 실험 번호 | 개수 | 행수 |
|---|---|---|---|
| Train (양품만) | 1, 2, 3, 11, 13, 14, 15, 17 | 8 | 14,654 (변경 없음) |
| Eval — 양품 | 12, 18, 22 | 3 | 5,094 |
| Eval — 불량 | 4, 5, 6, 7, 8, 9, 10, 16, 20, 21, 23 | 11 | 8,838 |

Eval 총 13,932행(양품 5,094 / 불량 8,838, 63.4%) — train은 리키지 대상이었던 24만
제외 대상이라 변경 없음. `total_rows`는 28,586(기존 32,048에서 3개 실험 3,462행 제외).

**영향**: 이 보정 전/후로 LSTM-AE 결과를 다시 비교한 결과, 리키지를 제거하니 수치가
오히려 더 좋아졌다(mean 방식 기준 precision 0.846→0.909, recall 0.917→0.909) — 즉
"CN7보다 훨씬 좋다"는 결론이 리키지 때문이 아니라 견고함이 재확인됐다. 상세 수치는
`2026-07-24-cnc-lstm-autoencoder-design.md`의 사후 보정 절 참고.

## 테스트 전략

CN7 전처리 스펙과 동일한 방식(실제 학습/전체 파이프라인 실행은 유닛테스트 대상이 아님):

- 라벨 도출 함수(`machining_finalized`+`passed_visual_inspection` → label)는 네 가지 조합
  (yes/yes, yes/no, no/blank 등) 합성 데이터로 테스트한다.
- 상수 컬럼 탐지 함수는 합성 배열(상수 컬럼 포함/미포함)로 테스트한다.
- 실험 단위 split 함수는 작은 합성 실험 세트로 "지정한 실험 번호의 모든 행이 정확히 한쪽에만
  들어가는지"(리키지 없음)를 테스트한다.
- 스케일링(train만 fit, eval transform-only)은 합성 데이터로 mean/std 계산과 리키지 없음을
  테스트한다.
- 실제 25개 실험 전체를 돌린 결과(최종 행수, 드롭 컬럼, 분할 구성)는 이 문서에 이미 실측
  기록된 수치와 대조해 수동 검증한다.
